## Hallazgos priorizados

### P1. Configuración y seguridad

#### 1. El nombre de la base no es único

Situación actual:

- `docs/GUIA-LABORATORIO.md` crea `aula_circular`.
- `.env.example` propone `aula_circular_sprint2_ensayo`.
- El `.env` del entorno revisado usa `aula_prueba_catalogo`.

Riesgo: aplicar migraciones o datos en una base distinta de la esperada, o creer que se está probando una base cuando el servidor usa otra. `/api/salud` solo ejecuta `SELECT 1`; no comprueba que el esquema o los datos sean los correctos.

Cambio recomendado: elegir un nombre canónico y usarlo en la guía, `.env.example`, `README.md` y los comandos de preparación. No renombrar ni borrar la base actual sin copia y autorización. El nombre `aula_prueba_catalogo` describe el entorno revisado, pero no consta como decisión del proyecto.

Estado: **no aplicado**. El cambio afecta a archivos fuera de `docs/`.

#### 2. `.docente-local.json` no está ignorado

`npm.cmd run docente:local` crea `.docente-local.json` con una contraseña ficticia local. El archivo no existe en la revisión actual, pero `.gitignore` no lo incluye. `docs/CUENTAS.md` afirmaba que estaba excluido de Git; esa afirmación se ha corregido en la documentación.

Riesgo: un `git add -A` o una publicación descuidada puede incluir credenciales locales. Aunque la cuenta sea ficticia, el archivo no debe llegar al repositorio.

Cambio recomendado:

1. Añadir `.docente-local.json` a `.gitignore`.
2. Comprobar con `git check-ignore -v .docente-local.json`.
3. Si el archivo ya estuviera versionado, retirarlo del índice sin borrar la copia local, con autorización.
4. Si alguna vez se publicó una contraseña, rotarla.

Estado: **no aplicado**. `.gitignore` está fuera del alcance documental actual.

#### 3. El marcador de `SESSION_SECRET` supera la validación mínima

`.env.example` contiene:

```text
SESSION_SECRET=GENERAR_UN_SECRETO_LOCAL_CON_EL_SCRIPT_PREPARAR
```

`src/app.mjs` solo comprueba que el secreto tenga al menos 32 caracteres. El marcador tiene 47, así que sería aceptado si alguien arranca sin ejecutar `npm.cmd run preparar`. El secreto sería predecible.

Cambio recomendado:

1. Rechazar expresamente el marcador conocido en `crearAplicacion` o en la carga de configuración.
2. Añadir una prueba que compruebe que el arranque falla con el marcador.
3. Mantener `npm.cmd run preparar` como paso obligatorio de la guía.

Estado: **no aplicado**. `src/app.mjs` y las pruebas están fuera del alcance actual.

### P2. Compatibilidad y legado

#### 4. URLs antiguas retiradas

Se comprobó:

- `/laboratorio/` responde 200.
- `/laboratorio` responde 301 hacia `/laboratorio/`.
- `/laboratorio.html` responde 404.
- `/catalogo.mjs` responde 404.

Si la documentación, una entrega o una prueba externa usa `/laboratorio.html` o `/catalogo.mjs`, dejará de funcionar. No consta una decisión sobre conservarlas.

Opciones:

- añadir redirecciones o alias compatibles; o
- documentar la retirada como cambio de contrato y actualizar a quien las use.

No se ha elegido ninguna. La decisión corresponde al equipo, con revisión del Team Leader.

#### 5. Código y pruebas de etapas anteriores

La aplicación activa se monta desde `src/app.mjs`. En el repositorio quedan piezas que no forman parte de ese recorrido:

- `src/auth.mjs` y `src/cuentas/*`: legado usado por `tests/` y scripts antiguos.
- `tests/`: pruebas legacy; `npm test` solo ejecuta `tests/`.
- `src/biblioteca/*`: no está montado en la aplicación activa y consulta tablas que no existen en las migraciones actuales (`categoria`, `recurso_curso`, `metadato_digital`). Montarlo sin adaptarlo produciría errores.
- `public/mjs/catalogo.mjs`: no se referencia desde las páginas actuales; la demo usa `public/laboratorio/catalogo.mjs`.
- `public/mjs/login.mjs`: conserva un comentario que menciona `src/cuentas/*`, aunque el login activo está en `src/app.mjs`.

Riesgo: que una persona nueva use el módulo equivocado, o que una prueba antigua se interprete como cobertura del estado actual.

Cambio recomendado: marcar estos elementos como legado, moverlos a una carpeta claramente separada o retirarlos después de revisar sus dependencias. Actualizar los comentarios y el mapa de archivos de la guía. Mantener `npm test` como suite activa.

#### 6. Documentación desalineada

La guía describía `src/app.mjs` como responsable de toda la API. En realidad `src/app.mjs` arranca Express y monta `src/app.mjs`; las rutas de catálogo están en `src/catalogo.mjs`. La guía también decía que `.gitignore` excluía `.docente-local.json`, lo que no era cierto.

Los documentos de Sprint 2 describen un estado intermedio y contienen rutas y SQL antiguos. Se han marcado como históricos para que no se confundan con el montaje actual.

Cambio recomendado: mantener una sola guía de montaje vigente y actualizar `README.md` cuando se decida el nombre de la base y la versión de PostgreSQL.

### P3. Versiones y cobertura

#### 7. PostgreSQL documentado frente a PostgreSQL instalado

El stack del proyecto y `README.md` indican PostgreSQL 17. La instancia revisada usa 18.6. No se ha comprobado si las migraciones, las pruebas y el SQL tienen alguna diferencia relevante en 18.

Opciones:

- usar PostgreSQL 17 en los equipos de la práctica; o
- validar y documentar PostgreSQL 18 como versión soportada.

No se ha decidido. Cambiar la versión del stack requiere revisión de la Dirección técnica y no debe hacerse solo en la guía.

#### 8. Cobertura de las pruebas

Las 17 pruebas actuales cubren cuentas, anuncios y el catálogo sobre el esquema actual. No cubren:

- el nombre de la base configurado;
- el rechazo del marcador de `SESSION_SECRET`;
- las URLs antiguas;
- el arranque con `.docente-local.json` sin ignorar.

Son candidatos para una comprobación de configuración antes de ampliar el alcance.

## Plan de cambios recomendado

Ninguno de estos pasos está aplicado. Antes de tocar configuración o código hace falta autorización separada.

1. **Decidir y documentar el nombre canónico de la base.** Actualizar guía, `.env.example`, `README.md` y cualquier comando de preparación. Hacer copia antes de renombrar o recrear.
2. **Cerrar el riesgo de credenciales locales.** Añadir `.docente-local.json` a `.gitignore`, comprobar el estado de Git y revisar si alguna credencial llegó a publicarse.
3. **Endurecer el arranque.** Rechazar el marcador de `SESSION_SECRET` y añadir una prueba de configuración.
4. **Decidir la compatibilidad de URLs.** Añadir redirecciones para `/laboratorio.html` y `/catalogo.mjs`, o documentar su retirada y actualizar consumidores.
5. **Separar el legado.** Marcar `src/auth.mjs`, `src/cuentas/*`, `src/biblioteca/*`, `tests/` y `public/mjs/catalogo.mjs` como históricos o retirarlos con revisión. No montar `src/biblioteca/*` sin adaptar sus tablas.
6. **Alinear versiones y documentación.** Decidir si se exige PostgreSQL 17 o se valida 18; actualizar `README.md` y la guía en consecuencia.
7. **Verificar el cierre.** Ejecutar `npm test`, `node --check` sobre los `.mjs` y las comprobaciones de URLs y configuración.
